# M3: Familiars as systemd units

## Decision

There is one lifecycle owner for each resident Pi: `familiar-pi@<instance>.service`.
Presence remains a small tmux TTY adapter, but neither Presence callers, the Go
supervisor, nor the gateway supervise Pi. The resulting process shape is:

```text
systemd familiar-pi@kestrel
  -> presence.sh start -> tmux server -> pane (MainPID) -> familiar.sh pi -> pi
viewer/gateway --------------------------------> tmux attach client -----^
```

Use `Type=forking` with `PIDFile=`. `presence.sh start` creates a detached tmux
session, reads `#{pane_pid}`, atomically writes `state/presence/pi.pid`, and
returns. systemd adopts that pane PID as `MainPID`. This is simpler than keeping
a headless attached tmux client alive: normal foreground tmux attach requires a
controlling terminal and adds a proxy process whose failure is unrelated to Pi.
The pane is still a real PTY that humans can attach to, while systemd observes
the process whose exit matters.

There is no respawn loop. `familiar.sh pi` execs Pi once, and the tmux pane does
not relaunch it. `Restart=always` and `RestartSec=1s` replace both old loops and
all calls to `ensure`. An explicit `systemctl stop` is not restarted by systemd.
The gateway is auth/client protocol/proxy only: viewer startup failure is
reported to the client. The Go supervisor has only `llm`, `stt`, `tts`,
`gateway`, and configured `plugin.golem.*` children.

Pi still receives `--continue`. Each instance has a separate config directory,
so `PI_CODING_AGENT_DIR` defaults to that directory's `state/pi`; `--continue`
therefore selects the most recent session for that instance, or creates one if
none exists. The unit exports `FAMILIAR_INSTANCE_ID=%i` for scheduler identity.
The mechanical deployment mapping below is:

```text
instance id kestrel
  config /var/lib/familiar/instances/kestrel/familiar.toml
  state  /var/lib/familiar/instances/kestrel/state/
  tmux   /var/lib/familiar/instances/kestrel/state/presence/tmux.sock
  PID    /var/lib/familiar/instances/kestrel/state/presence/pi.pid
```

Instance IDs must be systemd-safe names and directory names. Fort should create
the instance directory/config with the service user's ownership. Secrets and
plugin environment remain inputs to the unit (normally through `familiar.toml`
or the existing credential mechanism), not to the supervisor.

## fort-nix unit

Apply the equivalent of this module snippet, substituting the packaged Familiar
path, service account, and the existing fort instance root. The `%i` paths are
the only per-instance wiring.

```nix
{ pkgs, familiar, ... }:
{
  systemd.services."familiar-pi@" = {
    description = "Familiar Pi instance %i";
    after = [ "familiar-instance.service" ]; # ordering only; no Requires=
    serviceConfig = {
      Type = "forking";
      User = "familiar";
      WorkingDirectory = "/var/lib/familiar/instances/%i";
      PIDFile = "/var/lib/familiar/instances/%i/state/presence/pi.pid";
      ExecStart = "${familiar}/services/presence/presence.sh start";
      ExecStop = "${familiar}/services/presence/presence.sh stop";
      Restart = "always";
      RestartSec = "1s";
      KillMode = "control-group";
      TimeoutStartSec = "30s";
      TimeoutStopSec = "10s";
    };
    environment = {
      FAMILIAR_CONFIG_PATH = "/var/lib/familiar/instances/%i/familiar.toml";
      FAMILIAR_INSTANCE_ID = "%i";
      FAMILIAR_INTERACTIVE_SHELL = "${pkgs.bashInteractive}/bin/bash";
      FAMILIAR_PRESENCE_CWD = "/var/lib/familiar/instances/%i";
      FAMILIAR_PRESENCE_STATE_DIR = "/var/lib/familiar/instances/%i/state/presence";
      FAMILIAR_PRESENCE_SOCKET = "/var/lib/familiar/instances/%i/state/presence/tmux.sock";
      FAMILIAR_PRESENCE_PID_FILE = "/var/lib/familiar/instances/%i/state/presence/pi.pid";
    };
    path = [ pkgs.bashInteractive pkgs.coreutils pkgs.git pkgs.jq pkgs.nix pkgs.tmux ];
  };

  # For each configured instance (shown literally for clarity):
  systemd.targets.multi-user.wants = [ "familiar-pi@kestrel.service" ];
}
```

Fort diff checklist:

```diff
- familiar-instance-presence.service (monitor + ExecStop=presence.sh stop)
- familiar-instance.service Requires=familiar-instance-presence.service
- supervisor config child: presence -> presence.sh ensure
- gateway environment/lifecycle permission: FAMILIAR_PRESENCE_CTL
+ familiar-pi@.service above
+ enable familiar-pi@kestrel.service
```

Keep the server and Pi units independently restartable. `After=` only makes a
joint boot less noisy; Pi already waits for a required local LLM endpoint, and
a server redeploy must not bounce Pi.

## Cutover and rollback

1. Deploy this repository and the new unit definition while the old units are
   stopped; do not run old and new ownership concurrently. Back up the instance
   config and state (especially `state/pi`) first.
2. Disable/remove `familiar-instance-presence.service`; remove the old
   `Requires=` and the old supervisor presence child. Reload units, then enable
   and start `familiar-pi@kestrel` alongside the independent server unit.
3. Verify the Pi unit has the tmux pane as `MainPID`, `presence.sh status`
   succeeds, a viewer attaches without changing that PID, and one controlled
   Pi exit produces exactly one systemd restart with continuity restored.
4. Rollback by stopping/disabling `familiar-pi@kestrel`, restoring the previous
   repository/config and the old presence unit plus `Requires=`, then starting
   the old units. Do not restore or merge session files: both designs use the
   same `state/pi`; rollback is a process-ownership change, not data migration.
